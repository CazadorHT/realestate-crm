### **รายงานสรุปการทดสอบเชิงลึกแบบ "เทสโหด ไม่อวย" (Brutal Hardening & Zero-Trust Testing) ครบทั้ง 33 โมดูล**

เพื่อรับประกันเสถียรภาพระดับสูงสุดของสถาปัตยกรรม CRM V3 เราได้เปลี่ยนแนวทางการทดสอบจากแบบดั้งเดิม (Happy Path) มาใช้กลยุทธ์ **"Zero-Trust & Brutal Hardening"** โดยจำลองสถานการณ์เลวร้ายที่สุด ทั้งการโจมตีทางไซเบอร์, ฐานข้อมูลล่มกะทันหัน, ข้อมูลสูญหาย/ผิดรูป, ปัญหาการแย่งชิงทรัพยากร (Concurrency), และข้อจำกัดทางคณิตศาสตร์ 

ด้านล่างคือสรุปเจาะลึกวิธีการเทสโหดในแต่ละโมดูลจากทั้งหมด **33 โมดูล** ในระบบ:

---

### **🛡️ กลุ่มที่ 1: Core CRM & Entities (โมดูลหลักและระบบจัดการข้อมูล)**

#### **1. `properties` (ระบบจัดการอสังหาริมทรัพย์ - 13 ชุดทดสอบใหญ่)**
* **SQL Injection & XSS Flood:** ยิง Payload อันตราย (`' OR 1=1; DROP TABLE...`, `<script>alert(1)</script>`) เข้าไปในช่องค้นหาและฟอร์มสร้างทรัพย์ เพื่อทดสอบการสกัดกั้นผ่าน Zod และ Supabase RPC
* **AI Hallucination (AVM Valuation):** จำลองสถานการณ์ที่ AI ตอบกลับมาเป็น JSON ผิดรูปหรือสตริงขยะ เพื่อยืนยันว่าระบบ Fallback กลับไปใช้ค่าประเมินพื้นฐานโดยไม่เกิด Runtime Crash
* **Storage Outage & Orphan Prevention:** ตัดการเชื่อมต่อระบบ Storage ระหว่างอัปโหลดรูปภาพ เพื่อตรวจสอบระบบ Rollback ลบข้อมูลออกจากตารางหากบันทึกไฟล์ไม่สำเร็จ
* **Concurrent Update Race Conditions:** จำลองการแก้ไขทรัพย์เดียวกันพร้อมกัน 5 คำขอ เพื่อทดสอบกลไกป้องกันการล็อกตาราง (`40001: serialization failure`)

#### **2. `deals` (ระบบบริหารจัดการดีลและค่าคอมมิชชัน)**
* **Brutal Commission Diffing:** ทดสอบอัลกอริทึมคำนวณส่วนต่างค่าคอมมิชชันเมื่อมีการเปลี่ยนแปลงเงื่อนไขกะทันหัน โดยป้อนตัวเลขทศนิยมซ้ำซ้อนและค่าติดลบ (`-50000.9999`)
* **Foreign Key Lockouts:** จำลองการลบดีลที่มีสัญญาเช่าผูกมัดอยู่ (`23503: FK Violation`) เพื่อทดสอบการแจ้งเตือนข้อผิดพลาดที่สุภาพแทนการล่มของเซิร์ฟเวอร์
* **Mass Bulk Mutations:** สั่งอัปเดตสถานะดีลพร้อมกัน 5,000 ID เพื่อทดสอบขีดจำกัดหน่วยความจำ (Memory Leaks) และ Call Stack

#### **3. `leads` (ระบบบริหารจัดการผู้ติดต่อและโอกาสการขาย)**
* **Corrupted JSONB Parsing:** ป้อนข้อมูล `utm_data` และ `preferences` ที่โครงสร้างพัง (เช่น เป็น Array แทนที่จะเป็น Object หรือ String เปล่า) เพื่อทดสอบ Defensive Mapping ไม่ให้หน้าแสดงผลลัพธ์พัง
* **Extreme PII Boundaries:** ป้อนเบอร์โทรศัพท์ยาว 50 หลักและอีเมลที่ผิดไวยากรณ์ เพื่อทดสอบการสกัดกั้นก่อนถึงระดับฐานข้อมูล

#### **4. `owners` (ระบบบริหารจัดการเจ้าของทรัพย์)**
* **PDPA/GDPR Masking Failures:** ทดสอบระบบเข้ารหัสและถอดรหัสข้อมูลส่วนบุคคล (PII) โดยจำลองสถานการณ์ที่ Master Encryption Key หายไป เพื่อยืนยันว่าระบบล็อกข้อมูลและไม่เปิดเผยสตริงดิบ

#### **5. `co-brokers` (ระบบบริหารจัดการเครือข่ายตัวแทนร่วม)**
* **Division by Zero & NaN Injection:** ตรวจสอบระบบคำนวณอัตราปิดดีล (Conversion Rate) เมื่อตัวแทนมีจำนวนทรัพย์เป็น `0` และยอดขายเป็น `0` เพื่อรับประกันว่าระบบแสดงผลเป็น `0%` แทนที่จะเป็น `NaN` หรือ `Infinity`
* **Unique Index Collisions:** สั่งสร้างตัวแทนร่วมด้วยเบอร์โทรและอีเมลซ้ำซ้อน เพื่อทดสอบการดักจับรหัส `23505 (Duplicate Key)`

#### **6. `rental-contracts` & 7. `contracts` (ระบบบริหารจัดการสัญญาเช่า)**
* **Time Travel & Leap Year Edge Cases:** ป้อนวันที่เริ่มต้นและสิ้นสุดสัญญาในอดีต, อนาคตอีก 100 ปีข้างหน้า, และวันที่ 29 กุมภาพันธ์ เพื่อทดสอบความแม่นยำของระบบคำนวณค่าเช่าตามสัดส่วน (Prorated Rent)

### **💬 กลุ่มที่ 2: AI, Automation & Communications (โมดูลปัญญาประดิษฐ์และการสื่อสาร)**

#### **8. `chatbot` (ระบบ AI Chatbot อัจฉริยะ)**
* **429 Rate Limit & 503 Server Busy:** จำลองสถานการณ์ที่เซิร์ฟเวอร์ Gemini ทำงานหนักจนปฏิเสธคำขอ เพื่อทดสอบระบบทำซ้ำอัตโนมัติ (Exponential Backoff with Jitter)
* **Tool Calling Stress Test:** ป้อนคำถามกว้างๆ และคำถามซับซ้อนที่สะกดผิด เพื่อทดสอบความแม่นยำในการสกัดพารามิเตอร์ไปเรียกฟังก์ชัน `search_properties`

#### **9. `omni-channel` (ระบบศูนย์รวมการสื่อสารและแชท)**
* **Multi-Platform Flood:** จำลองการรับส่งข้อความพร้อมกันจาก LINE, Facebook, IG, และ WhatsApp โดยป้อนข้อความยาว 10,000 ตัวอักษรและอิโมจิซ้อนท้าย เพื่อทดสอบความทนทานของ Communications Hub
* **Just-in-Time Decryption Crash:** จำลองข้อผิดพลาดระหว่างถอดรหัส PII ของลูกค้าก่อนส่ง API เพื่อยืนยันว่าระบบแจ้งสถานะล้มเหลวเฉพาะข้อความนั้น โดยไม่กระทบข้อความอื่นในคิว

#### **10. `line` (ระบบจัดการเทมเพลต LINE)**
* **Malformed Template Configs:** ป้อนตั้งค่าเทมเพลต JSON ที่ไม่ถูกต้องและตัวแปรที่ไม่มีอยู่จริง เพื่อทดสอบระบบ Fallback ข้อความมาตรฐาน

#### **11. `rent-notifications` (ระบบแจ้งเตือนค่าเช่าอัตโนมัติ)**
* **Simulated Cron Execution Failures:** จำลองสถานการณ์ที่ไม่มีสัญญาเช่าที่ใช้งานอยู่ (No Active Contract) แต่ถูกทริกเกอร์ให้ส่งแจ้งเตือน เพื่อทดสอบกลไกป้องกันการส่งข้อความขยะหาลูกค้า
* **LINE Flex Message Integrity:** ทดสอบการสร้าง Flex Message ด้วยชื่อทรัพย์สินยาว 500 ตัวอักษรและราคาติดลบ เพื่อทดสอบการตัดคำ (Truncation) และการจัดรูปแบบตัวเลข

#### **12. `blog` & 13. `blogs` (ระบบ AI Blog Generator และ CMS)**
* **AI Format Breaker:** สั่งให้ AI เขียนบทความแต่จงใจส่ง Prompt ป่วนให้ AI ตอบกลับมานอกเหนือโครงสร้าง JSON ที่กำหนด เพื่อทดสอบกลไกซ่อมแซมโครงสร้างข้อมูล (Auto-Correction)
* **Bulk Deletion Outages:** สั่งลบบทความ 1,000 รายการพร้อมกัน พร้อมจำลองฐานข้อมูลล่มกลางคัน เพื่อทดสอบการรักษาสถานะข้อมูลไม่ให้สูญหายบางส่วน

### **📈 กลุ่มที่ 3: Analytics, Finance & Operations (โมดูลสถิติ การเงิน และการจัดการ)**

#### **14. `finance` (ระบบบัญชีและการคำนวณการเงิน)**
* **Absolute Floating-Point Precision:** ทดสอบการคำนวณภาษีหัก ณ ที่จ่าย (WHT), ภาษีมูลค่าเพิ่ม (VAT), และสัดส่วนคอมมิชชันด้วยตัวเลขทศนิยมซับซ้อน เพื่อยืนยันว่าไม่มีปัญหาเศษทศนิยมคลาดเคลื่อน (Rounding Errors)
* **Corrupted Ledger Summation:** ป้อนแถวข้อมูลค่าคอมมิชชันที่มีคอลัมน์จำนวนเงินเป็นสตริงขยะ (`"DROP TABLE"`, `"NaN"`) เพื่อทดสอบกลไกแปลงค่ากลับเป็น `0` อัตโนมัติ

#### **15. `analytics` (ระบบวิเคราะห์ข้อมูลและ KPI)**
* **Massive Aggregation Timeouts:** จำลองการดึงข้อมูล KPI ของตัวแทนและสรุปยอดขายย้อนหลัง 10 ปีที่มีข้อมูล 1,000,000 แถว พร้อมจำลองสถานการณ์ Gateway Timeout (`PGRST504`)

#### **16. `dashboard` (ระบบแดชบอร์ดสรุปผล)**
* **Widget Partial Crash Containment:** จำลองสถานการณ์ที่ Widget สรุปยอดขายล่ม แต่ Widget รายการนัดหมายยังทำงานปกติ เพื่อทดสอบสถาปัตยกรรม React Error Boundaries

#### **17. `calendar` (ระบบปฏิทินและการนัดหมาย)**
* **Cross-Tenant Hijacking Attempts:** พยายามสร้างและเลื่อนนัดหมายของลูกค้าที่อยู่ "คนละสาขา" (Tenant Isolation) เพื่อทดสอบกลไกสกัดกั้นระดับ RLS และ Server Action

#### **18. `documents` (ระบบจัดการเอกสารและสัญญา)**
* **Path Traversal & Negative File Sizes:** พยายามอัปโหลดไฟล์เอกสารด้วยชื่อไฟล์โจมตี (`../../../../etc/passwd`) และกำหนดขนาดไฟล์เป็น `-999999` ไบต์ เพื่อทดสอบความปลอดภัยของระบบจัดเก็บ

#### **19. `services` (ระบบจัดการบริการเสริมและทำความสะอาดไฟล์)**
* **Orphaned Media Cleanup Stress Test:** จำลองสถานการณ์ที่การลบไฟล์ภาพจาก Storage ล้มเหลว เพื่อทดสอบระบบบันทึกประวัติลง `activity_timeline_v3` และตามเก็บกวาดอัตโนมัติในภายหลัง (Self-Healing Storage)

### **⚙️ กลุ่มที่ 4: System, Configuration & Security (โมดูลระบบ การตั้งค่า และความปลอดภัย)**

#### **20. `admin` (ระบบบริหารจัดการส่วนกลางสำหรับผู้บริหาร)**
* **RBAC Escalation Protection:** จำลองผู้ใช้ระดับ `AGENT` และ `STAFF` พยายามเรียกใช้ฟังก์ชันอนุมัติผู้ใช้และดูรายงานงบประมาณ เพื่อทดสอบการดีดตัวกลับ (Unauthorized Access Abort)

#### **21. `audit` (ระบบบันทึกประวัติการใช้งานและ Audit Logs)**
* **Tamper-Proof Verification:** จำลองข้อผิดพลาดในการบันทึก Audit Log เพื่อยืนยันว่าระบบมีกลไกรับประกันไม่ให้ Log สูญหายแม้ระบบหลักจะทำงานหนัก

#### **22. `ai-monitor` (ระบบตรวจสอบการทำงานและค่าใช้จ่าย AI)**
* **Log Flood Resistance:** จำลองการส่งประวัติการใช้งาน AI รัวๆ 10,000 ครั้งใน 1 วินาที เพื่อทดสอบไม่ให้ตารางเก็บ Log บวมจนกระทบประสิทธิภาพฐานข้อมูลหลัก

#### **23. `ai-settings` (ระบบตั้งค่าโมเดล AI)**
* **Missing Config Fallbacks:** ลบการตั้งค่าโมเดล AI ออกจากระบบทั้งหมด เพื่อทดสอบการ Fallback กลับไปใช้ `gemini-1.5-flash` อัตโนมัติ

#### **24. `amenities` (ระบบสิ่งอำนวยความสะดวกและไอคอน)**
* **Missing Icon Key Resilience:** ป้อนชื่อไอคอนที่ไม่มีในระบบ เพื่อทดสอบระบบแสดงผลไอคอนสำรอง (Fallback Icon) โดยไม่ทำให้หน้าเว็บขาว

#### **25. `global` (ระบบค้นหาครอบจักรวาล)**
* **Multi-Table Query Exhaustion:** ทดสอบยิงคำค้นหาสั้นๆ (`"a"`) และคำค้นหาที่มีอักขระพิเศษ เพื่อทดสอบประสิทธิภาพการ Query ข้าม 4 ตารางใหญ่โดยไม่เกิดปัญหาคอขวด

#### **26. `line` (ระบบจัดการ LINE Webhook)**
* **Signature Verification Brutality:** ป้อน Webhook Payload ที่มี X-Line-Signature ปลอม เพื่อทดสอบระบบสกัดกั้นคำขอที่ไม่หวังดี

#### **27. `owners` (ระบบบริหารจัดการเจ้าของทรัพย์)**
* ทดสอบความทนทานต่อการค้นหาและอัปเดตข้อมูลเจ้าของทรัพย์สินพร้อมกันหลายรายการ

#### **28. `profile` (ระบบโปรไฟล์ผู้ใช้และช่องทางติดต่อ)**
* **Social Links Corruption:** ป้อนลิงก์โซเชียลมีเดียที่ผิดกฎและสตริงขยะ เพื่อทดสอบการทำความสะอาดข้อมูลก่อนบันทึกลง JSONB

#### **29. `public` (ระบบหน้าเว็บสาธารณะและฟอร์มติดต่อ)**
* **Bot Spam & RPC Failures:** ยิงฟอร์มติดต่อสอบถามรัวๆ 500 ครั้ง และจำลองสถานการณ์ฐานข้อมูลล่ม (`DB_DOWN`) เพื่อทดสอบการแจ้งเตือนผู้ใช้และการป้องกันสแปม

#### **30. `public-data` (ระบบข้อมูลสาธารณะและทำเลยอดนิยม)**
* **Cache Stampede Protection:** จำลองคำขอเปิดหน้า Landing Page พร้อมกัน 1,000 คำขอในจังหวะที่ Cache หมดอายุพอดี เพื่อทดสอบกลไก `unstable_cache` ป้องกันไม่ให้ฐานข้อมูลล่ม

#### **31. `site-settings` (ระบบตั้งค่าเว็บไซต์และ Smart Match)**
* **Schema Validation Brutality:** ป้อนการตั้งค่าเว็บไซต์ที่มีค่าผิดธรรมชาติ (เช่น เปอร์เซ็นต์การจับคู่ `-100%` หรือ `999%`) เพื่อทดสอบ Zod Schema

#### **32. `smart-match` (ระบบจับคู่ทรัพย์สินอัจฉริยะ)**
* **Weight Matrix Edge Cases:** ทดสอบระบบคำนวณคะแนนความเข้ากันได้ (Match Score) เมื่อเกณฑ์การค้นหาของลูกค้าไม่มีข้อมูล หรือทรัพย์สินมีข้อมูลไม่ครบ เพื่อรับประกันว่าอัลกอริทึมยังคำนวณคะแนนตามสัดส่วนที่เหลือได้แม่นยำ

#### **33. `system` (ระบบตรวจสุขภาพฐานข้อมูล - Realtime Doctor)**
* **Catastrophic Diagnostic Simulation:** จำลองสถานการณ์ที่ตารางหลัก (`notifications`) ล่ม พัง หรือติดปัญหา RLS เพื่อทดสอบระบบวินิจฉัยโรค (Realtime Doctor) ให้สามารถชี้เป้าสาเหตุของปัญหาได้อย่างแม่นยำ

### **🎯 สรุปภาพรวมความสำเร็จ (Executive Summary)**

จากการใช้กลยุทธ์การทดสอบแบบ **Brutal Hardening (เทสโหด ไม่อวย)** ทั้ง 33 โมดูล ส่งผลให้สถาปัตยกรรมของ CRM V3 มีคุณสมบัติระดับ **Ultra-Resilient (ทนทานขั้นสุด)** ดังนี้:
