# 💸 16: เครื่องยนต์กลไกการเงินขั้นสูง (Advanced Financials & Commission Engine)

> **กลไกที่ใช้:** Atomic PostgreSQL Operations, Advanced Fraction Logic, Dynamic Charts
> **อัปเดตล่าสุด:** 22 สิงหาคม 2026 (Enterprise v4.0 - August 2026 Release)
> **มิติของการขาย:** อาวุธลดความขัดแย้งของแผนกบัญชี

ระบบ CRM ที่ดีไม่ได้ทำแค่จดตัวเลขและแปะเศษสลึง แต่ต้องเป็นระบบ "ผู้ช่วยบัญชีประจำแฟรนไชส์" นี่คือส่วนที่แพงและซับซ้อนที่สุดของโปรเจค จนเรียกได้ว่าการตีความบรรทัดต่อบรรทัดของระบบการเงิน ช่วยให้เราขายซอฟต์แวร์นี้ได้ในราคาสูงที่สุด

## 1. สถาปัตยกรรมการหั่นคอมมิชชัน (Advanced Commission Splitting)

โลกความเป็นจริงของอสังหาริมทรัพย์ เซลล์ไม่ได้เก็บเงินคนเดียว โมเดลธุรกิจที่ซับซ้อนนี้ถูกเปลี่ยนให้กลายเป็นลอจิกคณิตศาสตร์ล้วนๆ

### 1.1 สามประสานแห่งผลประโยชน์ (The Tri-Split Approach)
เมื่ออสังหาขายออก 1 รายการ เงินก้อนที่ถูกโอนเข้ามาจะถูกสั่งการแยกส่วนอัตโนมัติดังนี้:
- **Listing Agent (ผู้หาทรัพย์):** ลอจิกจะตัดเปอร์เซ็นต์ส่วนแรกไปให้พนักงานที่เป็นคนดึงบ้านเข้าบริษัท
- **Closing Agent (ผู้ปิดงาน):** ลอจิกอีกกระหย่อมจะแบ่ง % ให้พนักงานที่พาลูกค้ามาจบดีล
- **Agency Pool (กงสีบริษัท):** ระบบคำนวณหักฝั่งบริษัทต้นสังกัดแยกต่างหากอย่างโปร่งใส 
- **หมายเหตุชั้นสูง:** โค้ดรองรับการสลับตัวผู้ปิดงาน หรือกรณีที่พนักงาน 1 คนสวมผ้าคลุมทั้งหาบ้านและปิดเอง (Dual Agency) โค้ดก็สามารถรวบสัดส่วนเงินได้โดยไม่ต้องป้อนมือซ้ำซ้อน

### 1.2 "Visual Split Bar" (แผนภูมิเงินเดือนแบบเห็นภาพชัดเจน)
ฝ่ายขายมักเกลียดตัวเลขบนตาราง Excel ยิบย่อย 
- ด้วยเทคโนโลยี React และ CSS หน้าจอดีล (Deal Details) จะเรนเดอร์แท็บกราฟสัดส่วนสีแนวนอน (Horizontal Stacked Bar)
- สีแดงแทนบริษัท สีน้ำเงินแทนฝ่ายหา สีเขียวแทนฝ่ายปิด ทำให้บอร์ดโชว์ตัวเลขที่ดูหน้าเบื่อ กลายเป็นภาพลวงตาที่มีพลังต่อกำลังใจการทำงาน

## 2. ล็อกคอภาษีสรรพากร (Tax Compliance & Net Amounts)

ระบบซอฟต์แวร์เมืองไทย ถ้าเขียนโง่ๆ คือเก็บแต่เงินเป้า (Gross) แต่เวลาจ่ายจริงบัญชีต้องมาปวดหัวกดเครื่องคิดเลข 

### 2.1 WHT 3% Automated Deductions (ระบบหัก ณ ที่จ่ายอัตโนมัติ)
- โค้ดฐานข้อมูลมีการฝังฟิลด์ที่เป็น `Computed Values` หากรายการระบุว่าต้อง หักภาษี ณ ที่จ่าย 3% ลอจิกหลังบ้านจะเป็นเงาตามตัวตัดยอดบัญชีนั้นๆ ออกจาก `net_amount` แจ้งผู้บริหารให้รู้จริงๆ ว่า "รายได้เข้าตู้เซฟ" มันไม่ใช่สิบล้านถ้วน แต่เป็นราคาที่ลบเศษภาษีออกแล้ว
- **ป้องกัน Error 100%:** ฝ่ายบัญชีไม่ต้องทะเลาะกับเซลล์เรื่องเศษทศนิยม เพราะ PostgreSQL ใช้ Type ข้อมูลแบบ `numeric(12,2)` (Fixed-point arithmetic) ไม่เกิดอาการคอมพิวเตอร์แปลงจุดทศนิยมพลาดแบบภาษา Javascript ทั่วไป (เช่น 0.1 + 0.2 = 0.300000004) แน่นอน!

## 3. Executive Stats Dashboard (แผงควบคุมระดับจักรพรรดิ)

เพื่อให้ CEO ที่กดปุ่ม "Switch Branch" (ตามบทที่ 05) ดูตัวเลขบริษัทข้ามสาขา การประมวลผลตัวเลขระดับนี้จะหนักเกินกว่าฝั่งมือถือของประธานจะทำไหว 

### 3.1 Caching Analytics Layer (อุ่นฐานข้อมูล)
- กราฟแท่งรายได้รายไตรมาส ของทุกสาขารวมกัน ใช้คำสั่งการเข้ารหัสก้อน SQL ดึงข้ามเซิร์ฟเวอร์แบบมัดรวม (Aggregation View)
- กราฟที่ประมวลผลแล้วนี้ จะถูกยิงไปพักตัวรออยู่ในหน้าจอล่วงหน้า และถูกทำ แคช (Edge Caching) 
- ดังนั้น หาก CEO ล็อกอินดูแดชบอร์ดช่วงพักเที่ยง หน้าจอไม่ได้มานั่งสั่งโหลด Database 5 แสนแถวใหม่ แต่กางสไลด์โชว์ขึ้นมาหน้าเว็บได้ดุจสายฟ้าฟาด 

_ทั้งหมดนี้คือการแฝงกระบวนทัศน์ Enterprise ERP (Enterprise Resource Planning) เข้าไปบรรจุเป็นหนึ่งคอร์หลักของ CRM ธรรมดา ทำให้ระบบนี้เป็นซอฟต์แวร์เกรดเดียวกับกลุ่มอุตสาหกรรมการเงินเลยครับ_
