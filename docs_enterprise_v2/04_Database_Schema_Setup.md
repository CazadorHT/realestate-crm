# 🏛️ 04: สถาปัตยกรรมฐานข้อมูลระดับลึก (Enterprise Database & Schema Engine)

> **เทคโนโลยี:** PostgreSQL 15+, Supabase (RLS & Triggers), `pg_trgm` GIN Index
> **แนวคิด:** ข้อมูลคือกระดูกสันหลัง ห้ามให้แอปเลเยอร์เป็นคนตัดสินใจฝั่งเดียว

หากเปรียบ Next.js คือใบหน้าและแขนขา **PostgreSQL Schema** ในโมเดลสถาปัตยกรรมนี้คือ "สมองส่วนจิตใต้สำนึก" ที่คอยปฏิเสธคำสั่งแปลกประหลาดที่ขัดแย้งกับหลักความเป็นจริง 

---

## 1. กติกา "ความเป็นเจ้าของแบบขังเดี่ยว" (Tenant Isolation)

หัวใจสำคัญของการที่มหาชนระดับนายหน้าแฟรนไชส์หลายหมื่นคนใช้ร่วมกันได้คือ Policy ที่โปร่งใส

### 1.1 กระบวนทัศน์ Row-Level Security (RLS) แบบเหล็กไหล
โปรเจคนี้ลบความเชื่อผิดๆ ที่ว่า "ให้ Backend หุ้มคำสั่ง WHERE บน Query" เพราะโปรแกรมเมอร์มักลืม!
ฐานข้อมูลตารางทุกเส้นที่มีมูลค่า (Deals, Properties, Contacts) จะถูกสลักคำสั่งล็อกด้วย RLS:
```sql
-- ตัวอย่างหลักการ
CREATE POLICY "Strict Tenant Isolation" ON deals
  FOR ALL
  USING (
    tenant_id = (select auth.jwt() -> 'app_metadata' ->> 'current_branch_id')
  );
```
**ผลลัพธ์:** ต่อให้มีเซียนแฮกเกอร์โจมตีข้ามมารัน API ดึงข้อมูลได้ ถ้าตัว JWT Token ไม่ใช่พนักงานสาขานั้น Database ก็จะส่งค่ากลับมาเป็นศูนย์ตอกหน้าไปทันที! การันตี 100% Data Breach Prevention

---

## 2. อะตอมมิกสแตก (Atomic RPC) และ Optimistic Locking

เราย้ายตัวตัดสินใจธุรกิจลงลึกสู่ชั้น SQL Functions (Stored Procedures / RPC) เพื่อลบระบบ "เชื่อใจเวลา" ออกไป

### 2.1 อวสานปัญหาสต็อกป่วน (Race Condition)
เวลาเอเยนต์ 2 คนคุยกับแอดมินเพื่อจองคอนโดห้องเดียวกัน แล้วกดปุ่ม "เปลี่ยนสถานะเป็น Reserved" ในเวลาห่างกัน 0.1 วินาที! หากให้ระบบ API หน้าบ้านทำ มันจะอ่านข้อมูลขัดแย้ง 
**การแก้ปัญหา (Atomic Trigger Engine):**
1. ทุกการเข้าคิวเปลี่ยนสถานะบ้าน จะผ่าน **RPC function** ที่ชื่อเช็ค `version` ของข้อมูลควบคู่ไปด้วย (Optimistic Locking)
2. คนแรกที่กด `version` จะขยับจาก 1 -> 2 สำเร็จ
3. คนที่สองที่กดเสี้ยววินาทีตามมา จะโดน Data Engine ตบกลับด้วย Error ทันที เพราะ `version` ที่ถือมาเป็น 1 ไม่ตรงกับใน DB ปัจจุบัน 
4. หมดปัญหา "คนจ่ายเงินไม่ได้ห้อง คนได้ห้องไม่ได้จ่ายเงิน" เชิงลึก!

### 2.2 คืนชีพประวัติด้วย Soft Deletes (The Immortal Row)
ไม่ว่าจะหน้ามืดโมโหขนาดไหน พนักงานที่กดลบ "บิลคอมมิชชันรายล้าน" หรือ "สัญญาลูกค้า" จะไม่ทำลายข้อมูลนั้นออกจากแผ่นดิสก์ ทุกตารางสำคัญติดตั้งโครงสร้างตาราง `deleted_at (timestamp)` แทนคำสั่ง DELETE (Hard delete) ทำให้ Timeline ไม่แหก และเจ้านายสามารถกู้คืน (Undelete) ทุกแอ็กชันได้ราวกับย้อนเวลา

## 3. เขี้ยวเล็บแห่งการค้นหาภาษาไทย (`pg_trgm` GIN Index)

ลูกค้าอสังหาริมทรัพย์มักค้นหาด้วยคำที่พิมพ์ตกหล่น เช่น "คอนโตะ สุขุมวิช" หรือ "หอพักราคาถูก" การใช้ Query แบบ `.ilike` ธรรมดาตอนหาบ้าน หมื่นหลังใน Database จะทำให้ CPU ของ PostgreSQL โหลดนานกว่า 3 วินาที

**เราแก้ไขด้วย GIN (Generalized Inverted Index):**
ฐานข้อมูลเปิดใช้ extension นามแฝง **Trigram Matching** (`pg_trgm`) ซึ่งจำแนกชุดข้อมูลตัวหนังสือออกเป็น 3 อักขระ ทำให้ระบบสามารถดึงบ้านที่สะกดคำ "ใกล้เคียง" ออกมาได้ในระดับ มิลลิวินาที (ms) แม้จะสะกดผิดเบาๆ

## 4. โครงสร้างตารางและนโยบายจัดเก็บข้อมูลล่าสุด (v4.0 Schema & Storage Extensions)

### 4.1 ตารางระบบย่อยใหม่ (New Enterprise Tables)
- **`popular_areas`**: จัดเก็บทำเลทองยอดนิยม (ชื่อทำเล, พิกัด Lat/Lng, คำค้นหาอ้างอิง, ลำดับการแสดงผล, และสถานะการใช้งาน) เชื่อมโยงเข้ากับระบบ `MagicAiSearch`
- **`system_configs`**: จัดเก็บการตั้งค่าระบบส่วนกลางและ Metadata ในรูปแบบ JSONB พร้อมระบบ Caching ในหน่วยความจำฝั่ง Node.js

### 4.2 นโยบายการจัดเก็บรูปภาพ (Supabase Storage Buckets & Policies)
- **`property-images`**: จัดเก็บภาพถ่ายอสังหาฯ และรูปภาพที่ผู้ฝากขายอัปโหลดผ่านแบบฟอร์มฝากขาย Public
- **`social-cards`**: จัดเก็บภาพการ์ดโฆษณาที่ส่งออกผ่าน **Social Studio** สำหรับส่งต่อให้ TikTok Catalog & Meta API
- **Public Read Access**: สิทธิ์การอ่านไฟล์ถูกกำหนดเป็น Public Read เพื่อรองรับ CDN HTTP Header Caching (`max-age=31536000`) โดยยังจำกัดสิทธิ์การ Write/Delete เฉพาะ Authenticated Users เท่านั้น
