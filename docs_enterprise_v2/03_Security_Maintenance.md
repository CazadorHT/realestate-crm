# 🛡️ 03: สถาปัตยกรรมความปลอดภัย (Enterprise Security & Maintenance)

> **กลไกความปลอดภัยหลัก:** Upstash Redis, HMAC SHA-256 Webhooks, Idempotency Keys, API Rate Limiting
> **เป้าหมาย:** สกัดกั้นการโจมตีจากผู้ไม่หวังดี ป้องกันค่า API AI โดนเผา และกำจัดปัญหาข้อความแชทเด้งซ้ำ

ในระบบ Cloud-based CRM ระดับสเกลใหญ่ "ความปลอดภัยและขีดจำกัด" คือจุดตายที่ชี้วัดว่าระบบจะไปรอดไหมในช่วงแคมเปญใหญ่ (เช่น งานมหกรรมบ้านและคอนโด) สถาปัตยกรรมความปลอดภัยนี้ถูกออกแบบมาเพื่อ **ซับแรงกระแทก (Shock Absorption)** และบล็อกการกระทำที่ส่งผลร้ายต่อฐานข้อมูลหลักอย่างชาญฉลาด

---

## 1. Upstash Redis: ปราการด่านหน้าแห่ง Rate Limiting

ระบบจะเรียกฟังก์ชันเช็คประวัติการยิง API ผ่าน ฐานข้อมูลแบบ In-memory ชั้นแนวหน้า (Upstash) เพื่อบังคับ **API Rate Limit** ก่อนคำสั่งจะถึง Next.js เซิร์ฟเวอร์เสมอ

### 1.1 โควต้าการใช้งานแบบเป็นขั้นบันได (Tiered Bucketing)
เพื่อป้องกันไม่ให้แบน User จริงที่เพียงแค่เน็ตกระตุก ระบบจึงใช้กลไกการนับแบบ Token Bucket Algorithm โดยแบ่งเป็น:
- **Public Endpoints (เช่น ค้นหาบ้าน):** 100 requests / 10 วินาที / IP
- **Auth Endpoints (เช่น Login):** 5 requests / นาที ป้องกันการทำ Brute-force สุ่มรหัสผ่านพนักงาน
- **Heavy Data APIs:** การสั่งดึงสถิติใหญ่ที่มีผลต่อ CPU จะดรอป Limit ลงเหลือ 10 Req/min
หากระบบพบว่า IP ใดล้ำเส้น ตัว Middleware ที่ฝังอยู่ที่ขอบข่ายขอบเซิร์ฟเวอร์ (Vercel Edge Network) จะตอกกลับด้วยรหัส **429 Too Many Requests** อัตโนมัติ โดยไม่ต้องรบกวน CPU ของเรา 

### 1.2 "AI Kill Switch" (กำแพงป้องกันเงินรั่วถัง)
การเรียกใช้ AI เช่น ปุ่มประเมินราคา AVM หากโดนบอท (หรือคู่แข่ง) เข้ามายิงปุ่มรัวๆ งบประมาณอาจละลายหายหลักแสน
- ผู้ใช้งานแต่ละระดับจะถูกผูกเข้ากับ Rate Limit โควต้าของ AI (เช่น Agent รันได้ 50 ครั้ง/วัน)
- ผสานคู่ไปกับข้อมูลจาก `ai_usage_logs` ฝั่ง PostgreSQL เมื่อยอดเงินถึงลิมิต ระบบจะเกิดการ "ตัดไฟ (Circuit Break)" ไม่ให้กดอีกทันที

## 2. พลังของ "ระบบต้านการทำซ้ำ" (Idempotency Protection)

หนึ่งในรอยทะลุที่คลาสสิกที่สุดของแพลตฟอร์มระดับโลกคือการทำงานของ Webhook ขาเข้าจาก LINE พัง

### 2.1 Webhook Replay Attacks และปัญหาแชทเด้งรัว
สมมติว่าเซิร์ฟเวอร์ LINE OA กระตุก หรือผู้ใช้เชื่อมไวไฟโรงแรม ยิงกดบันทึกลูกค้ามาหาโค้ดของเรา 3 รอบ สิ่งที่เกิดคือ ลูกค้าจะถูกสร้าง 3 คนซ้ำๆ เกิดข้อมูลขยะ

### 2.2 Redis Request Signature Locks
ทุก Webhook ที่ถูกยิงเข้ามา จะถูกถอด Payload มาทำการเข้ารหัส Hashing เป็น "Signature Idempotency Key"
- หากมี Key เดิมส่งตามมาในระยะเวลา 5 วินาที Redis จะโต้ตอบว่า "ฉันกำลังทำอันเก่าอยู่ หรือทำเสร็จไปแล้ว" (Conflict/Locked)
- ส่งผลให้ การชนกันของข้อความ LINE หรือการกดปุ่มบันทึกบ้านรัวๆๆ (Double Clickers) จะถูกตีกลับโดยฐานข้อมูลไม่เจ็บตัวแม้แต่รอยขีดข่วน

## 3. กลไก HMAC SHA-256 (พิสูจน์ศพผู้ส่งข้อความ)

เมื่อเปิด API แบบ Public ในฝั่ง Meta (Facebook) และ LINE เราจะรอดพ้นแฮกเกอร์ได้อย่างไร?
- โค้ดของเราไม่ได้ทำงานทันทีที่ข้อมูลถูกส่งเข้ามา
- ระบบจะหยิบ X-Line-Signature มาถอดสมการด้วย **HMAC SHA-256** ทาบกับ Channel Secret ฝั่งเรา
- เป็นประตูเหล็กกันภัย ว่าข้อมูลแชทลูกค้ามาจากเซิร์ฟเวอร์ของ LINE จริงๆ ไม่ใช่โปรแกรม Postman ที่ถูกยงจากแฮกเกอร์ชาวรัสเซีย

_บันทึกสำหรับดูแลระบบ: ห้ามตั้งค่า Redis Token หรือ Secret Keys เหล่านี้ลงไปในไฟล์โค้ดเด็ดขาด ต้องฝังผ่าน Environment Variables ในเซิร์ฟเวอร์ Hosting เสมอ_
